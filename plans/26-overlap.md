# 重叠时光 Overlap

给异地恋和跨时区团队算"每天到底有几小时能同时清醒又都有空"的计算器。核心计算是红海（同类产品一搜一大把），真正的护城河全在情绪化的命名、可分享的卡片和持续累加的"共同清醒小时数"里程表。

**核心体验与情绪钩子**
钩子是把冰冷的时差换算成有温度的"我们每天只重叠 2 小时 47 分"，让分隔两地的人第一次直观看到彼此有多稀缺。给重叠窗口起名（早安吻、道晚安）和实时倒计时把工具变成陪伴感的载体，戳中异地恋的思念情绪。这是典型的"情绪 > 功能"打法。

**详细玩法与规则**
输入两个（或多个）城市/时区，再各自设置睡眠时段和上班/忙碌时段。系统扣掉睡眠与工作后，算出所有人"都醒着且都空闲"的黄金重叠窗口，可能是连续一段或分散几段。给每段窗口自动命名：清晨那段叫"早安吻"，睡前那段叫"道晚安"。结果页顶部是重叠总时长，中间是里程表（累计共同清醒小时数，持续跳动），底部是"距下一个重叠窗口还剩 X 分钟"的实时倒计时。

**分享卡设计**
主视觉一句话"我们每天只重叠 2 小时 47 分"，配两个城市名与各自当前时间的小时钟图标。卡片下半展示命名过的窗口条（早安吻 07:00-08:00）和已累计的共同清醒小时数。风格温柔、适合发对方或发朋友圈秀恩爱，水印域名放角落。

**留存与回访**
核心留存靠"攒数字"：共同清醒小时数只增不减，像旅行纪念里程一样让人舍不得离开、每天想回来看一眼。做可选的倒计时提醒（下一个重叠窗口开始前推送"该说早安了"），把工具变成每日打卡的关系仪式。设纪念节点（累计 100 小时、恋爱满 1 年）触发特殊卡片。

**技术实现**
时区计算是关键且易错，务必用成熟库（Luxon / date-fns-tz + IANA 时区数据库）处理夏令时，不要手算 UTC 偏移。重叠、命名、倒计时都是纯前端逻辑；"攒数字"和提醒需要轻后端存配对关系（一个短链 ID 对应两地设置），可用 Serverless + KV 存储。倒计时用本地计时器，提醒用 Web Push 或邮件。

**防滥用/反作弊/内容安全**
共同清醒小时数是情感数字，要防用户改系统时间刷数——以服务端时间为准累计，客户端只展示。分享链接含双方城市与作息，属弱隐私，需可随时重置/删除配对。避免存真实身份信息，配对用随机 ID 而非账号。

**冷启动与宣发**
主攻异地恋社区：小红书"异地恋"话题、豆瓣异地小组、微博超话，以真实情侣的分享卡做种子内容。副线打跨时区远程团队（"我们团队只有 1.5 小时能同时在线"），在即刻/X 的远程办公圈传播。情人节、七夕、520 集中投放，配合"晒你们的重叠时长"UGC 挑战。

**盈利模式**
工具型吃 SEO 长尾（"北京 纽约 时差 重叠时间"这类查询）养 AdSense，但单价低需规模。更现实的变现是情侣向增值：定制主题皮肤、纪念日长图、去水印、"关系纪念册"一次性付费。切忌指望展示广告养活，把重叠卡当引流入口，靠情感产品做转化。

**MVP 范围与开发量**
MVP = 双城市输入 + 睡眠/工作时段设置 + 重叠计算与命名 + 一张分享卡。纯前端 1-2 周可出，"攒数字"和提醒属第二阶段（需后端），先验证分享卡是否被传播再投入。

**主要风险与化解**
最大风险是计算本身是红海、无技术壁垒——必须承认这点，把资源全押在情绪化命名、分享卡颜值和"攒数字"体验上，用户留下来是因为舍不得那个累计数字而非算得准。其次是异地恋是刚需但用户生命周期有限（分手或团聚即流失），靠拓展跨时区团队和好友场景扩大人群。夏令时/时区算错会毁口碑，用成熟库严格测试化解。
